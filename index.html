Real-Time E-Commerce Data Platform

Kafka · PySpark · Airflow · dbt · Snowflake · Docker

repo ↗

An end-to-end platform processing 50K+ synthetic events daily across separate streaming and batch paths — transactional events, product/catalog data, and currency enrichment modeled and orchestrated independently, then reconciled in the warehouse layer.

architecture

[ingest] Python Kafka producer → PySpark Structured Streaming: transformation, null handling, type validation, enrichment, checkpoint-based fault-tolerant recovery → curated Parquet on S3/MinIO.

[transform] 20+ dbt models (staging → intermediate → mart), star schema, SCD Type 2 customer dimension for historical tracking.

[orchestrate] Airflow: ingestion → validation → COPY INTO Snowflake → dbt run → data-quality checks → Slack alert on failure.

[quality/ci] Great Expectations + GitHub Actions; Kafka/Spark/Airflow/MinIO containerized via Docker Compose for reproducible dev.

design decision

Two independent paths (streaming + batch) instead of one unified pipeline — event-level latency and catalog-level consistency have different failure tolerances, so coupling them would've meant either slowing down events or risking half-updated catalog state.

failure handling

Checkpoint-based recovery on the Spark side means a consumer restart resumes from last committed offset, not zero — no duplicate-processing cleanup needed after a crash.

Engineering Thinking

Tools are the easy part to list. These are the actual calls — what I chose, what I turned down, and why — pulled from real production work, not a buzzword grid.

reliability

Runbooks over heroics

10+ DAGs owned end-to-end meant failures couldn't all route through me personally. I chose to spend time writing runbooks and structuring alerts so someone else could triage a failed DAG without paging me first — that's what actually cut manual intervention by 60%, not the pipelines being "more correct."

performance

Fix the access pattern, not the hardware

The Glue/Athena workflow was slow because it was scanning full tables on every run. The instinct is to scale the cluster up; I looked at the query pattern instead and added partition pruning to eliminate the redundant scans — same infra, 68–80% faster, and it stayed fast as data volume grew instead of needing another scale-up later.

data modeling

SCD Type 2 where history actually matters

Not every dimension needs to track history — it's extra storage and join complexity. I used SCD Type 2 specifically on the customer dimension, where "what did we know at the time" changes the answer to real business questions, and kept simpler patterns elsewhere instead of applying it everywhere by default.

system boundaries

Streaming and batch don't share a failure budget

On the e-commerce platform, event ingestion and catalog updates run as two separate paths instead of one unified pipeline. They have different latency and consistency requirements — coupling them would mean either slowing down real-time events or risking a half-updated catalog. Keeping the boundary explicit kept both sides simpler.
